# Phase 1 – Data layer: interview Q&A

What we built: Postgres schema (doctors, schedules, patients, appointments) with SQLAlchemy 2.0 and
Alembic, an idempotent synthetic seed, and pure timezone-aware services for slot generation and
booking validation. Code: `src/medagent/db/`, `src/medagent/services/`, `migrations/`.

---

### Why store everything in UTC but define working hours in Europe/Berlin?
An instant in time is unambiguous in UTC, so comparing, sorting and range-querying timestamps is
safe. But "Dr. Smith works 08:00–17:00" is a *wall-clock* rule: it must stay 08:00 locally when the
clock changes for daylight saving. So the schedule stores naive local `time` values, and the
service converts to UTC only when generating concrete slots. The clinic timezone is a setting
(`CLINIC_TIMEZONE`), so another clinic only changes config.

### What bugs did the legacy code have, and how did you fix them?
- Naive `datetime.now()` and naive DB columns: ambiguous across servers/timezones → timezone-aware
  everywhere; naive input raises `ValueError`.
- Hard-coded 08:00–20:00 in two places (availability and validation) that could drift → one
  `DoctorSchedule` table, one slot generator used by both.
- Check-then-insert booking (race condition) → a database unique index.
- Services opened their own DB sessions and returned display strings → pure functions that take
  data in, and return typed results (`BookingError` enum); wording is the caller's job.

### How do you prevent two people booking the same slot?
With a constraint in the database, not an `if` in Python. Two concurrent requests can both see the
slot as free and both insert; only a unique index is atomic. The loser gets an `IntegrityError`,
which `repository.create_appointment` translates into `SlotTakenError` for the agent/API to turn
into "that slot was just taken, here are others".

### Why a *partial* unique index (`WHERE status = 'booked'`)?
A plain `UNIQUE (doctor_id, start_time)` would also block rebooking a slot after a cancellation,
because the cancelled row still exists. The partial index only constrains active bookings, while
keeping cancelled rows for history/audit.

### What does "pure function" buy you here?
`generate_slots`, `free_slots`, `validate_slot` take schedules, bookings, `now` and the timezone as
arguments: no DB, no global clock, no LLM. Tests need no mocks and can pin "now" to any instant
(DST days, midnight boundaries). Later, LangGraph tools just fetch data via the repository and call
these functions, so business rules aren't scattered across prompts.

### Walk me through the DST edge cases you handle.
- Slots are built by stepping local wall-clock time, then converting to UTC, so 08:00 is 07:00 UTC
  in winter and 06:00 UTC in summer.
- On spring-forward day (2027-03-28) 02:00–03:00 doesn't exist. We round-trip each slot through UTC
  and skip any wall-clock time that doesn't survive. Tested.
- Known limitation: on fall-back day, the repeated hour is only bookable once (first occurrence).
  Acceptable because clinics aren't open at 02:00; documented rather than hidden.
- Day queries use `[local midnight, next local midnight)` converted to UTC (`clinic_day_bounds`),
  so that day can be 23 or 25 hours long, never assumed to be 24.

### What is SQLAlchemy 2.0's `Mapped[]` style and why use it?
Columns are declared with Python type annotations (`Mapped[int]`, `Mapped[str | None]`);
nullability comes from the type (`| None`), and `mapped_column()` adds details. mypy (strict) then
understands model attributes, so `appointment.start_time` is a `datetime`, not `Any`.

### What is Alembic and why not `create_all()`?
`create_all` only creates missing tables; it can't alter a live database. Alembic keeps versioned,
reviewable migration scripts (`upgrade`/`downgrade`) so every environment, including production,
reaches the same schema in order. `env.py` reads the URL from settings and imports the models so
`--autogenerate` can diff them against the DB. A naming convention on `MetaData` gives every
constraint a stable name, which is what lets Alembic drop/alter them later. I always read the
autogenerated script (e.g. I added `CREATE EXTENSION vector`, since autogenerate can't know).

### How do you test the database layer?
Unit tests cover the pure services (DST, boundaries, lunch breaks, off-grid times). Integration
tests (`@pytest.mark.integration`) create a throwaway `medagent_test` database, run the *real*
migrations into it (so migrations are tested too), and check: double booking is rejected, a
cancelled slot can be rebooked, CHECK constraints reject bad status/weekday, UTC round-trips, seed
idempotency, and the DB → services pipeline. CI runs them against a pgvector Postgres service.

### Why is the seed idempotent?
Re-running must never duplicate rows or fail (it's run in dev, CI and deploys), so it looks up by
natural key (doctor name, patient email) and only fills in what's missing, including topping up a
partially seeded database. Test: seed twice → second run creates 0 rows.

### Why synthetic data instead of real or scraped data?
- **GDPR / privacy:** health-related and personal data is a special category. With fully synthetic
  data there is no data subject, no lawful-basis question, no breach risk, and nothing to delete on
  request. Patients use `example.com` emails and fictional phone numbers; no PII enters the repo,
  logs or traces. The doctors are random first/last-name combinations, so any resemblance to real
  people is coincidental; I never scraped directories (also avoids licence/ToS problems).
- **Reproducibility:** a fixed seed means every laptop, CI job and deployment gets the identical 100
  doctors, so tests, evals and demos are stable and a failing test can be reproduced anywhere.
- **Realistic scale:** 15 doctors made routing trivial. 100 doctors over 19 specialties, 10 cities
  and mixed languages/schedules exercise filtering, ranking and slot logic the way production would.

### How does the Faker seed stay deterministic *and* idempotent?
`generate_doctor_specs(seed, total)` is a pure function: `Faker("de_DE")` seeded per instance
(`seed_instance`) plus a seeded `random.Random` for the choices (cities, languages, schedule
pattern). It always generates the *whole* list in the same order, regardless of what is already in
the database; `seed()` then inserts only the specs whose name is missing. Same inputs → same
doctors; re-runs → no changes. Names are kept unique inside the generator, since the DB is matched
by name. The 15 original doctors are hard-coded and come first, so their specialties are always there.
Because the seed runs in deployed environments too, Faker is a runtime dependency, not dev-only.

### How did you model varied working hours?
A pool of schedule patterns (full day with lunch 12–13, shifted lunch, long lunch, early shift, late
shift, 4-day week, part-time mornings/afternoons, a long no-break day) is assigned per doctor. Each
becomes `DoctorSchedule` rows (one per weekday per block), so a lunch break is just two blocks.
Languages and city live on `Doctor` (a Postgres `ARRAY` column and an indexed string), added in a
second migration with server defaults so existing rows migrated cleanly. Language filtering uses the
array `@>` operator (`Doctor.languages.contains([...])`).

### Why enable the pgvector extension in this phase?
The first migration is the schema's single source of truth, and Phase 2 (RAG) needs `vector`.
`CREATE EXTENSION IF NOT EXISTS` is safe to repeat, and the Docker image already ships pgvector.

### What would you do differently at scale?
- Add an `end_time`/duration column if appointment lengths vary, with an exclusion constraint
  (`btree_gist` + range type) to prevent *overlapping* bookings, not only identical start times.
- Handle the fall-back repeated hour explicitly.
- Per-doctor time off / holidays table feeding the slot generator.
- Async SQLAlchemy + connection pooling tuned for the API workload (Phase 5).
